# Vendored reference bakes

Tier two of `BuiltinTransform` handling (docs/impl/ocio.md §4.1). The OCIO v2
ACES configs express their output transforms as **code names** — "ACES-OUTPUT —
… SDR-VIDEO" — not as data, so there is nothing in the config file to read. The
design's answer is to generate those transforms once, offline, with the
reference OpenColorIO library, and check the resulting artefact in like any
other golden data.

**Nothing is vendored yet.** A style with no bake here and no direct
implementation in `src/builtin.rs` refuses by name, which is the correct
behaviour rather than a gap being papered over. `src/builtin.rs` carries the
loader; this directory carries the data when someone with the reference library
generates it.

## What a bake must carry before it can land here

One file per style, in the format `bake::VendoredArtefact` reads (`to_text` /
`from_text`). The first line is exactly `lumit-colour artefact 1`; every `#`
line after it is provenance, and these five are required:

```
lumit-colour artefact 1
# style: ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - SDR-100nit-REC709_2.0
# generated by: OpenColorIO <version>, <how it was invoked>
# generated from: <config file name, at <release tag>>
# generated on: <date>
# input domain: shaper lg2, min -8, max 5, offset 0.00390625
shaper lg2 -8 5 0.00390625
cube 65
0 0 0
…
```

A file without those lines is not a golden, it is a table somebody found.

## The bake-generation recipe (K-489)

Same session, same library version, same day as
`../tests/fixtures/aces-cg.fixture` — see that directory's README for the
install and the config download, which this recipe assumes have already
happened. **The bake and the rows that prove it must come from one run.** A
bake generated in March and a fixture generated in June agree only by luck, and
the suite would report that luck as fidelity.

The shaper is not a choice. It is `Shaper::DEFAULT` — `lg2`, `min -8`,
`max 5`, `offset 0.00390625` — and the cube is 65³ (`bake::CUBE_SIZE`), because
the sampler on the graphics card is compiled against exactly those numbers. A
file with different ones parses and then samples wrong.

Save as `bake.py` beside the config and run
`python bake.py "<style name>" > "<style name>.artefact"`.

```python
"""Bake one BuiltinTransform style with the reference OpenColorIO library.

The grid, the shaper and their order are Lumit's — see bake.rs — and nothing
here may drift from them. Only the VALUES come from the reference library.
"""
import sys, math, datetime, PyOpenColorIO as ocio

STYLE = sys.argv[1]
CONFIG = "cg-config-v4.0.0_aces-v2.0_ocio-v2.5.ocio"   # record which
SIZE, MIN_LOG2, MAX_LOG2, OFFSET = 65, -8.0, 5.0, 0.00390625

def shaper_inverse(t):
    """Cube coordinate 0–1 back to the scene-linear value it stands for.

    The mirror of Shaper::Lg2::inverse in bake.rs. Transcribe it, do not
    re-derive it: an offset applied on the wrong side of the exponent shifts
    every sample by a fraction of a stop and still produces a picture.
    """
    return 2.0 ** (t * (MAX_LOG2 - MIN_LOG2) + MIN_LOG2) - OFFSET

# The style, resolved through a config so the library builds it exactly as it
# would for a view that names it.
t = ocio.BuiltinTransform(style=STYLE, direction=ocio.TRANSFORM_DIR_FORWARD)
cpu = ocio.Config.CreateFromFile(CONFIG).getProcessor(t).getDefaultCPUProcessor()

print("lumit-colour artefact 1")
print(f"# style: {STYLE}")
print(f"# generated by: OpenColorIO {ocio.GetVersion()}, vendored/README.md's bake.py")
print(f"# generated from: {CONFIG}")
print(f"# generated on: {datetime.date.today()}")
print(f"# input domain: shaper lg2, min {MIN_LOG2:g}, max {MAX_LOG2:g}, offset {OFFSET}")
print(f"shaper lg2 {MIN_LOG2:g} {MAX_LOG2:g} {OFFSET}")
print(f"cube {SIZE}")

# RED FASTEST — blue is the outer loop. That is Lumit's order everywhere
# (docs/impl/lut.md §1) and it is the OPPOSITE of CLF's, so a script copied
# from a CLF writer transposes red and blue. The file is read back
# positionally, and a transposed cube is the classic silent LUT bug: it
# survives every test that only looks at neutrals.
last = SIZE - 1
for b in range(SIZE):
    lb = shaper_inverse(b / last)
    for g in range(SIZE):
        lg = shaper_inverse(g / last)
        for r in range(SIZE):
            out = cpu.applyRGB([shaper_inverse(r / last), lg, lb])
            print(f"{out[0]!r} {out[1]!r} {out[2]!r}")
```

Then add the style to `vendored()` in `src/builtin.rs` — the registry is a
`match` on the style name returning `VendoredArtefact::from_text`, so an entry
is one `include_str!` arm — and add its rows to `aces-cg.fixture` from the same
session.

## Which builtins the ACES 2.x configs need first

Read off `cg-config-v4.0.0_aces-v2.0_ocio-v2.5.ocio` (ACES 2.0, OCIO 2.5), which
is the smallest of the published configs and therefore the shortest path to one
that loads end to end. Eighteen styles appear in it. Four are implemented
directly today (`builtin::IMPLEMENTED`); the rest are the debt, in the order
they are worth doing:

**Two are one line each and want no bake at all** — they belong in tier one:

- `pass_thru` — the identity under a second name, and it refuses today purely
  because the name is not in the table.
- `ACEScc_to_ACES2065-1` — the ACEScc log, Academy S-2014-003, beside the
  ACEScct that is already written out in `builtin.rs`.

**Four output transforms need bakes.** These are the ACES 2.0 rendering
transform, which is code and not a composition, so there is nothing to write
out by hand:

- `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - SDR-100nit-REC709_2.0`
- `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - SDR-100nit-P3-D65_2.0`
- `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - HDR-1000nit-P3-D65_2.0`
- `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - HDR-1000nit-REC2020_2.0`

**One look needs a bake**: `ACES-LMT - ACES 1.3 Reference Gamut Compression`.

**Eight display encodings** are each a primaries matrix and a documented
transfer function, so they are tier-one candidates rather than bakes — except
that five of them say **MIRROR NEGS**, meaning the curve is mirrored about zero
for negative input, which the op set does not express yet:

- `DISPLAY - CIE-XYZ-D65_to_sRGB - MIRROR NEGS`
- `DISPLAY - CIE-XYZ-D65_to_G2.2-REC.709 - MIRROR NEGS`
- `DISPLAY - CIE-XYZ-D65_to_REC.1886-REC.709 - MIRROR NEGS`
- `DISPLAY - CIE-XYZ-D65_to_G2.6-P3-D65 - MIRROR NEGS`
- `DISPLAY - CIE-XYZ-D65_to_DisplayP3` and `…_to_DisplayP3-HDR`
- `DISPLAY - CIE-XYZ-D65_to_REC.2100-PQ` and `…_to_ST2084-P3-D65`

A config loads end to end only when *every* style its views reach is answered,
so the shortest useful target is one display and one view: `pass_thru`, the
Rec.709 output transform, and the Rec.1886 Rec.709 display encoding. That is
one bake, one style port, and one mirrored-curve decision.

## Why the bakes are not simply approximated in Rust in the meantime

Because a wrong picture that looks plausible is the one failure this crate is
built to refuse. An exact Rust port of each style is recorded follow-up work,
one style at a time, each landing against these same fixtures — at which point
the style moves from tier two to tier one and the vendored file becomes the test
data that proves the port.
