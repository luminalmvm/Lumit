# Vendored reference bakes

Tier two of `BuiltinTransform` handling (docs/impl/ocio.md §4.1). The OCIO v2
ACES configs express their output transforms as **code names** — "ACES-OUTPUT —
… SDR-VIDEO" — not as data, so there is nothing in the config file to read. The
design's answer is to generate those transforms once, offline, with the
reference OpenColorIO library, and check the resulting artefact in like any
other golden data.

## What is vendored

Five artefacts, 47 MiB, all from one PyOpenColorIO 2.5.2 session on 2026-08-25
against `cg-config-v4.0.0_aces-v2.0_ocio-v2.5.ocio` — the same session that
produced `../tests/fixtures/aces-cg.fixture`:

| Style | Size |
|---|---|
| `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - SDR-100nit-REC709_2.0` | 9.7 MiB |
| `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - SDR-100nit-P3-D65_2.0` | 9.7 MiB |
| `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - HDR-1000nit-P3-D65_2.0` | 9.3 MiB |
| `ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - HDR-1000nit-REC2020_2.0` | 9.3 MiB |
| `ACES-LMT - ACES 1.3 Reference Gamut Compression` | 9.3 MiB |

Each is 65³ samples at nine significant digits, which is what an `f32` needs to
round-trip and about a third of the size of Python's own `repr`. They are **not**
compiled into the binary — 47 MiB riding in every build was the cost of the
first cut, and it was removed. `src/builtin.rs` reads them at runtime, style
name as file name, from the first directory that exists: `data/colour/` beside
the executable (a shipped Windows or Linux build), `Contents/Resources/colour/`
(a shipped macOS bundle), then this directory (a development checkout, which is
also what the tests read). The packaging scripts copy them in —
`packaging/windows/build-installer.ps1`, `packaging/macos/make-dmg.sh` and
release.yml's Linux staging step — and a file that is absent leaves its style
refusing by name, exactly as if it had never been vendored.

A vendored artefact becomes **ordinary chain steps** rather than getting its own
execution path: the lg2 shaper *is* a log curve with a lin-side offset, and the
cube *is* a 3D table over 0–1, so a bake composes with a display encoding like
anything else. The chain is re-baked downstream onto the same 65-point grid with
the same shaper, so the samples land back on the points they came from.

**What a bake costs at the gamut edge is measured, stated and gated**: 0.117 at
the Rec.709 blue primary through the Rec.709 SDR output transform, against better
than 2 × 10⁻³ inside the gamut. §5.4 carries the number and the reason;
`aces-cg.fixture` carries the rows. Porting a style to tier one is what tightens
it, and those rows are what a port will be measured against.

## What a bake must carry before it can land here

One file per style, in the format `bake::VendoredArtefact` reads (`to_text` /
`from_text`). The first line is exactly `lumit-colour artefact 1`; every `#`
line after it is provenance, and these five are required:

```
lumit-colour artefact 1
# style: ACES-OUTPUT - ACES2065-1_to_CIE-XYZ-D65 - SDR-100nit-REC709_2.0
# generated by: OpenColorIO <version>, <how it was invoked>
# generated from: <config file name, at <release tag>>
# generated on: <date>
# input domain: shaper lg2, min -8, max 5, offset 0.00390625
shaper lg2 -8 5 0.00390625
cube 65
0 0 0
…
```

A file without those lines is not a golden, it is a table somebody found —
and `builtin::tests::every_vendored_style_has_an_artefact_with_its_provenance`
says so out loud rather than letting a truncated file surface as a wrong picture.

## The bake-generation recipe

Same session, same library version, same day as
`../tests/fixtures/aces-cg.fixture` — see that directory's README for the
install and the config download, which this recipe assumes have already
happened. **The bake and the rows that prove it must come from one run.** A
bake generated in March and a fixture generated in June agree only by luck, and
the suite would report that luck as fidelity.

The shaper is not a choice. It is `Shaper::DEFAULT` — `lg2`, `min -8`,
`max 5`, `offset 0.00390625` — and the cube is 65³ (`bake::CUBE_SIZE`), because
the sampler on the graphics card is compiled against exactly those numbers. A
file with different ones parses and then samples wrong.

`bake.py` is checked in beside the artefacts. Run it from this directory:

```sh
python bake.py "<style name>" > "<style name>.artefact"
```

Read it before changing it. The two things it must not get wrong are the shaper
inverse — transcribed from `bake.rs`, not re-derived, because an offset applied
on the wrong side of the exponent shifts every sample by a fraction of a stop
and still produces a picture — and the cube order. **Red is fastest**, blue is
the outer loop. That is Lumit's order everywhere (docs/impl/lut.md §1) and it is
the OPPOSITE of CLF's, so a script copied from a CLF writer transposes red and
blue. The file is read back positionally, and a transposed cube is the classic
silent LUT bug: it survives every test that only looks at neutrals. That is why
`builtin::tests::a_vendored_cube_is_read_in_the_order_it_was_written` checks a
grid point with three *different* indices against the reference library's own
answer there.

Then add the style to `VENDORED` in `src/builtin.rs` — the registry is that
list: `vendored()` only looks on disk for a style the list names, and the style
name is the file name, so a new bake is one list entry and one file here.

## Which builtins the ACES 2.x configs need — the debt as it now stands

Read off `cg-config-v4.0.0_aces-v2.0_ocio-v2.5.ocio` (ACES 2.0, OCIO 2.5), the
smallest of the published configs. Eighteen styles appear in it, and **all
eighteen are now answered**, so that config resolves end to end.

**Tier one, implemented directly** — fourteen styles in `builtin::IMPLEMENTED`:

- `IDENTITY` and `pass_thru` (the identity under a second name);
- `ACEScc_to_ACES2065-1`, `ACEScct_to_ACES2065-1`, `ACEScg_to_ACES2065-1`;
- `UTILITY - ACES-AP0_to_CIE-XYZ-D65_BFD`;
- all eight display encodings. Each is a primaries matrix derived from its own
  chromaticities plus a documented transfer function run backwards, which is
  literally the reference library's own decomposition of them. Six use the
  mirrored curve `Op::Negatives` now expresses — including
  `DisplayP3` and `DisplayP3-HDR`, whose names do not say MIRROR NEGS but whose
  decomposition does — and the two PQ ones use `Op::Pq`, SMPTE ST 2084 as a
  tier-one curve rather than a 65536-entry table.

**Tier two, the five bakes above.** The ACES 2.0 rendering transform is code and
not a composition, so there is nothing to write out by hand.

**What is left is the upgrade, not a gap.** Exact Rust ports of the five baked
styles, one at a time, each landing against the `aces-cg.fixture` rows that gate
the bake it replaces — at which point the style moves from tier two to tier one,
the 0.117 gamut-edge figure comes down, and the vendored file becomes the test
data that proves the port. A style in neither tier still refuses by name; the
ACES 1.x output transforms (`… - SDR-VIDEO_1.0`) are the nearest example and
`builtin::tests::an_output_style_with_no_bake_refuses_by_name` holds it.

## Why the bakes are not simply approximated in Rust in the meantime

Because a wrong picture that looks plausible is the one failure this crate is
built to refuse. A bake is not an approximation of the reference — it *is* the
reference, sampled — and every place it falls short of exact is measured, stated
and gated rather than hoped about.
